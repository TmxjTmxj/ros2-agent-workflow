# Agent 工具链对比：Codex / Claude Code + DeepSeek / Hermes + DeepSeek 在同一 ROS2 项目中的表现

> 本文记录 2026-08-12 ~ 2026-08-14 期间，三条不同 Agent 工具链在同一个 ROS2 项目
> （`ros2-smartcar-competition` → 泛化为 `ros2-agent-workflow`）中的真实表现对比，
> 以及由此沉淀出的"多 Agent 分工"通用解。
>
> **核心结论先行：工具不同确实会导致 Agent 控制 ROS2 的结果差异——差异不在"会不会用 ROS2"，
> 而在"长程任务的韧性"与"从理解到产出的收敛能力"。视觉是次要因素，不是决定因素。**

---

## 一、背景：同一个项目，三条 Agent 线

| 工具链 | 模型 | 承担的角色 | 时间 |
|--------|------|-----------|------|
| **Codex CLI** | OpenAI 系 | 攻坚：泛化框架 + 完整验证闭环 | 08-12 下午 ~ 08-13 |
| **Claude Code CLI** | DeepSeek V4 Flash | 发布：检索参考 / GitHub 发布 / README / review 测试 | 08-12 早 + 08-13 |
| **Hermes Agent** | DeepSeek V4 Flash | 守关：赛题调研 / 测试修复 / 验收证据核实 | 08-13 ~ 08-14 |

## 二、三条线的真实表现（数据来自会话记录）

### 1. Codex — 攻坚者（端到端交付）

- 将 24m×18m 医院配送场景泛化为通用框架 `ros2-agent-workflow`
- 完成 `examples/hospital_delivery` 完整赛题案例：MCP 桥、Fail-Closed 安全网关、独立验收监控器
- **验收结果：任务 SUCCEEDED，49.6s，三段端点误差 0.325/0.337/0.341 m（≤0.50m），零碰撞，停止漂移 0.0088m**
- **322 项自动化测试全绿**
- 产出架构图、安全状态机、双语图文 README

**特征**：从"泛化设计"到"跑通验证"到"测试全绿"是一条完整的长链，中途不换手、不放弃，
体现长程任务的韧性（数百轮工具调用中推理链不断）。

### 2. Claude Code + DeepSeek V4 Flash — 发布者（单步任务极稳）

会话记录统计（主会话 2.7MB，725 次模型调用）：

| 指标 | 数值 |
|------|------|
| 工具调用 | 285 次（Bash 256 / Edit 15 / Read 13 / Ask 1） |
| 错误结果 | **0 次** |
| 完成内容 | 检查 Codex 进度 → gh CLI 发布 GitHub → 图文 README → review 循环测试 → 与旧项目合并 |

**特征**：
- **单步明确任务（发布、写文档、跑测试、合并）做得干净利落，零错误**
- 但在另一个会话（创建 `smartcar_bringup` 功能包）中，**做了 20 次侦察（ls/cat/grep/Read）却没有一次 Write/Edit**——
  陷入"调研深坑"，没有收敛到产出。这是"理解强、收敛弱"的典型表现
- 遇到 Codex 写的测试挂起（`test_singleton_*`）时，能用 review 循环方法**逐步二分定位**（对比改动前后、逐个测试定位），调试方法系统

### 3. Hermes + DeepSeek — 守关者（验证与沉淀）

- 赛题调研：确认真实比赛为"中国机器人大赛暨 RoboCup · 送药巡诊机器人赛项"（7m×7m 官方场地）
- 修复 `tests/support/__init__.py` 缺失 → **322 测试全绿**
- 核实验收报告：`elapsed_seconds = 49.6159`，任务 SUCCEEDED，证据链完整（发布者 GID 监控 / 接触监控 / 相机截图）
- 将验收证据（JSON + 相机 PNG）入库 `evidence/`，修正 README 比赛口径

**特征**：不做核心攻坚，做"验证、修复、归档"——交叉检查 Codex 的产出，保证"可信"。

## 三、为什么工具不同会导致区别？

### 1. 模型的长程韧性（决定性差异，约占 70%）

ROS2 项目最难的不是"写 ROS2 代码"，而是**马拉松式排障**：重心参数两难（0.070 转向正常但偏航、
0.035 左转失效）、rclpy 版本不匹配、rosbridge 不可靠——每轮都是"改参数 → 跑仿真 → 看数据 → 分析 → 再改"。
这类任务要求模型在**上百轮工具调用中保持推理链不断、记得之前试过什么、不重复踩坑**。

- **Codex 的模型**：后训练侧重长程 agent 任务，在这类马拉松调试中更稳
- **DeepSeek V4 Flash**：单轮深度推理强（八皇后/命理/写作全过），但长程多步任务的韧性弱一档
- 证据：V4 Flash 做"明确单步任务"0 错误；做"从零建包"这种开放式任务时陷在调研里 20 步没产出

### 2. 从"理解"到"产出"的收敛能力

- Codex：理解 → 直接产出（写完整个框架 + 测试）
- Claude Code + V4 Flash：理解很充分（读了很多配置文件），但**收敛到写代码的能力弱**——
  侦察了 20 步没有落笔，这是"读得多、写得少"的典型 V4 行为
- Hermes + V4：同样在"验证类"任务稳，不承担"从零产出"类任务

### 3. 产品形态的适配

| 工具 | 形态优势 | 适配任务 |
|------|---------|---------|
| Codex CLI | 工作区管理、自动提交、测试运行集成 | 长程代码攻坚 |
| Claude Code CLI | 轻量、Edit 精准、单步命令稳 | 发布、文档、局部修改、测试 |
| Hermes Agent | 通用网关、MCP、cron、跨 Agent 记忆桥 | 调研、验证、编排、沉淀 |

### 4. 视觉的角色（次要）

有视觉能看 Gazebo 截图辅助判断，但 ROS2 调试**主要靠位姿数据、日志、测试输出**（全是文本）。
**就算给 V4 配上眼睛，也变不成 Codex——差距在脑，不在眼。**

## 四、通用解：多 Agent 分工模式（后人少走弯路）

基于本次实践，**单 Agent 全包不是最优解**。推荐以下分工：

```
┌──────────────────────────────────────────────────────┐
│                多 Agent 分工模式                        │
├──────────────────────────────────────────────────────┤
│  攻坚者 (长程模型)                                      │
│  · 适合: Codex / o 系列 / 长程强的模型                  │
│  · 负责: 框架设计、核心实现、马拉松排障、验收闭环         │
├──────────────────────────────────────────────────────┤
│  执行者 (便宜快模型)                                    │
│  · 适合: Claude Code / Cursor + V4 Flash 等            │
│  · 负责: 检索参考、建包、发布、文档、跑测试、合并         │
│  · 单步任务零错误，但避免分配"从零建复杂系统"类开放任务    │
├──────────────────────────────────────────────────────┤
│  守关者 (验证 Agent)                                    │
│  · 适合: Hermes / 第二个独立 Agent                      │
│  · 负责: 赛题调研、测试修复、验收证据核实、文档归档        │
│  · 价值: 交叉检查，保证"可信"，防伪造                    │
└──────────────────────────────────────────────────────┘
```

### 给后人（Agent 控制 ROS2 项目）的 5 条建议

1. **按任务深度选工具**：单步/机械任务（发布、文档、跑测试）→ 便宜快模型即可；
   长程攻坚（调试、泛化、验收）→ 必须用长程韧性强的模型。用 V4 类模型攻坚长程调试，
   会大量消耗时间在"读得多、写得少"上。

2. **给 Agent 的任务要"可验证、有收敛标准"**：开放式任务（"创建一个功能包"）会让
   V4 类模型陷入调研深坑；应拆成"创建 package.xml + setup.py + 入口脚本，然后 colcon build 验证"
   这种有明确成功判据的任务。

3. **交叉验证是硬要求**：验收数据必须由**独立监控器**生成（本项目的 evidence 机制），
   并由第二个 Agent 复核。Codex 声称的"322 测试全绿"，由 Hermes 复核并修复
   `tests/support` 后才真正成立。

4. **证据链入库**：验收报告 JSON + 相机截图随仓库发布（`examples/hospital_delivery/evidence/`），
   "防伪造"不是口号，是仓库里躺着的事实。

5. **版本与依赖的坑要提前写进交接文档**：ROS2 Lyrical 的 rclpy 是 3.14 C 扩展 vs 系统 Python 3.11
   不匹配、gz topic CLI 每次调用 0.5s 开销、地面摩擦 mu 必须双修——这些坑不写下来，
   换一个 Agent 又要重新踩一遍。

---

## 五、结论

1. **工具不同确实导致结果不同**，核心差异在模型的长程韧性与收敛能力，不在视觉。
2. **没有万能 Agent**：Codex 攻坚强、V4 单步稳、Hermes 验证准——各有所长。
3. **最优解是"攻坚者 + 执行者 + 守关者"的多 Agent 分工**：让每个模型站在它最擅长
   的位置上，用交叉验证保证可信，用文档沉淀避免重复踩坑。
4. 这个模式不限于 ROS2——任何"长程攻坚 + 大量机械操作 + 需要可信验证"的项目都适用。
